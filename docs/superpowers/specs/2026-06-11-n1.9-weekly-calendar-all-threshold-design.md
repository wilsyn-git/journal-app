# N1.9 — Weekly calendar `'all'` unreachable with mixed reset days

**Date:** 2026-06-11
**Issue:** N1.9 (med) — `docs/newissues.md:61-64`, `docs/issuesMerged.md:63`
**Scope:** Single-file pure-logic fix in `lib/rules.ts`. No schema, no migration, no write-path change.

## Problem

`computeRuleCalendarStatus` (`lib/rules.ts:361-403`) classifies each calendar date as
`'all'` / `'partial'` for a user's rule completions. Weekly completions are keyed
`week-<resetDate>-R<resetDay>` (see `getPeriodKey`, `lib/rules.ts:37-61`), and the
calendar buckets them by `<resetDate>`.

Because a date encodes its weekday, the `<resetDate>` in a key is always a date whose
weekday equals `resetDay`. Completions for different reset days therefore land in
**different date buckets** — buckets are already implicitly partitioned by reset day.

The bug: the `'all'` threshold (`lib/rules.ts:398`) compares each bucket's completion
count against `weeklyAssignments.length` — the count of **all** weekly assignments
across **every** reset day:

```js
weeklyStatus[sundayDate] = count >= weeklyAssignments.length ? 'all' : 'partial'
```

When a user has weekly rules with **mixed reset days** (e.g. one Sunday-reset, one
Wednesday-reset), no single date bucket can ever reach the global total, so `'all'`
is unreachable and the calendar shows `'partial'` even when every rule due on that
reset day was completed.

- Only affects users who mix weekly reset days. The default uniform-Sunday reset
  behaves correctly today.
- Pre-existing; not introduced by the N2.1 refactor (which preserved this behavior
  exactly). There is **no overwrite/collision** — distinct reset days never collapse
  to the same date bucket.

## Desired semantics (confirmed)

A weekly date bucket reads `'all'` when **every weekly rule due on that reset day** is
completed. Rules on other reset days are irrelevant to that bucket.

## Fix

All changes in `lib/rules.ts`, in/around `computeRuleCalendarStatus` (lines 351, 384-400).

1. **Capture the reset day in the regex.** `WEEKLY_KEY_RE` (line 351) currently captures
   only the date:

   ```js
   const WEEKLY_KEY_RE = /^week-(\d{4}-\d{2}-\d{2})-R\d+$/
   ```

   Change to also capture the reset day:

   ```js
   const WEEKLY_KEY_RE = /^week-(\d{4}-\d{2}-\d{2})-R(\d+)$/
   ```

2. **Precompute per-reset-day assignment counts** from `weeklyAssignments`, normalizing
   the reset day with the **same `?? 0`** that `getPeriodKey` uses (`lib/rules.ts:50`),
   so a null `resetDay` buckets as `R0` consistently with how its keys are written:

   ```js
   const weeklyGroupSizes = new Map() // resetDay (number) -> assignment count
   for (const a of weeklyAssignments) {
     const rd = a.rule.ruleType.resetDay ?? 0
     weeklyGroupSizes.set(rd, (weeklyGroupSizes.get(rd) ?? 0) + 1)
   }
   ```

3. **Compare each bucket against its own reset-day group size.** In the bucket loop
   (lines 395-399), extract the reset day from the key (regex group 2) and size the
   `'all'` check against the matching group:

   ```js
   for (const [periodKey, count] of weeklyCounts) {
     const match = WEEKLY_KEY_RE.exec(periodKey)!
     const resetDate = match[1]
     const resetDay = Number(match[2])
     const groupSize = weeklyGroupSizes.get(resetDay) ?? count
     weeklyStatus[resetDate] = count >= groupSize ? 'all' : 'partial'
   }
   ```

The daily branch (lines 369-382) is **untouched** — daily rules have no reset-day
partition, so its global-count threshold is already correct.

## Why this is safe

- **Behavior-preserving for the common case.** With a uniform reset day (the default
  Sunday), every weekly assignment is in one group, so `groupSize ==
  weeklyAssignments.length` and the output is byte-identical to today. This holds the
  same bar N2.1 set ("byte-for-byte identical" for existing behavior).
- **Contained.** One file, one pure function. No schema, migration, write path, or API
  change. No prod-data interaction.
- **Output shape unchanged.** `weeklyStatus` stays keyed by `<resetDate>` (line 397
  semantics preserved). Distinct reset days never collide on a date key, so there is no
  map-key collision risk.

## Edge cases

- **Empty / vacuous `'all'`:** every bucket in `weeklyCounts` originates from a
  completion, which implies a live assignment for that reset day, so `groupSize >= 1`.
  The `?? count` fallback is belt-and-suspenders only (would never trigger in practice).
- **Null `resetDay`:** normalized to `0` on both the key-writing side (`getPeriodKey`)
  and the grouping side (step 2), so they stay consistent.
- **Malformed keys:** already filtered by `WEEKLY_KEY_RE.test` before counting
  (line 390), unchanged.

## Testing

Extend `tests/lib/ruleCalendarData.test.ts` (already 11 cases from N2.1). Add:

1. **Mixed reset days, both groups fully completed** — two weekly rules, one Sunday-reset
   (R0) and one Wednesday-reset (R3), each completed on its own reset-date bucket →
   each bucket reads `'all'`. (This is the regression case — fails before the fix.)
2. **Mixed reset days, one group partial** — within a single reset-day group of two
   rules, only one completed → that bucket reads `'partial'`.
3. **Null resetDay groups as R0** — a rule with `resetDay: null` and a Sunday-reset
   rule (R0) share a bucket and threshold correctly.
4. **Regression guard** — existing uniform-Sunday cases remain `'all'`/`'partial'`
   exactly as before.

Run the full suite (`npm test`) to confirm all prior cases are unchanged.
