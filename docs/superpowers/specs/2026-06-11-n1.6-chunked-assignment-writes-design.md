# N1.6 — Bounded "assign to all" via chunked writes + consolidated resolver

**Date:** 2026-06-11
**Issue:** N1.6 (med) — `docs/issuesMerged.md`, `docs/newissues.md:46-49`
**Scope:** Consolidate a duplicated helper, chunk assignment inserts, add observability. No schema, no migration, no dependency change. Code-only deploy.

## Problem

When an admin creates/updates a rule or task with assignment mode `ALL`, the code:
1. Does an unbounded `prisma.user.findMany({ where: { organizationId } })` to resolve every user in the org (`app/actions/rules.ts:33-38`, `app/actions/tasks.ts:27-32` — **byte-identical duplicates**), then
2. Inserts one assignment row per user in a **single `createMany`** inside a `$transaction`
   (`rules.ts:246`, `rules.ts:312`, `tasks.ts:85`, `tasks.ts:165`).

Two real risks:
- **Correctness on large orgs.** Each assignment row binds ~3 variables (`id`, `ruleId`/`taskId`, `userId`). A single `createMany` for a few hundred+ users can exceed SQLite's per-statement variable limit (999 on builds before 3.32), causing the whole operation to fail. The same applies to the `createTask` push lookup `deviceSession.findMany({ where: { userId: { in: userIds } } })` (`tasks.ts:97-104`), whose `IN (...)` clause has the same limit.
- **No visibility.** Nothing logs how many assignments an `ALL` operation produced, so a growing org gives no signal until something is slow or breaks.

The original issue text proposed "batch the inserts (`createMany`) instead of N sync inserts," but `createMany` is **already** in use — so that half is done. This spec addresses the genuine residual: chunk the writes so they are statement-safe at any org size, consolidate the duplicated resolver, and add count logging.

## Decisions (confirmed)

- **No hard cap / no refusal.** Large orgs are processed in sane chunks rather than blocked.
- **Chunk size: 200** (`ASSIGNMENT_INSERT_CHUNK_SIZE`). At ~3 vars/row this stays well under the 999-variable floor, so it is correct on conservative SQLite builds.
- **Warn threshold: 1000** (`LARGE_ASSIGNMENT_WARN_THRESHOLD`). Advisory only — logs a warning when an `ALL` resolve exceeds it.
- **Atomicity preserved.** Chunked inserts stay inside the existing `$transaction`; a rule/task and all its assignments still commit or roll back together.
- **Consolidate** the resolver into a shared, db-injected module.

## Design

### New module: `lib/assignmentTargets.ts`

```typescript
import { ASSIGNMENT_MODES } from '@/lib/taskConstants'

/** Batch size for assignment createMany inserts — keeps each statement safely
 *  under SQLite's per-statement variable limit (999 on builds before 3.32). */
export const ASSIGNMENT_INSERT_CHUNK_SIZE = 200

/** When an ALL-mode resolve exceeds this many users, log a warning. Advisory
 *  observability signal only — does not block the operation. */
export const LARGE_ASSIGNMENT_WARN_THRESHOLD = 1000

/** Minimal structural client so this is unit-testable with a mock
 *  (mirrors the HealthCheckDb pattern in lib/health.ts). */
export interface AssignmentTargetsDb {
  userGroup: {
    findUnique: (args: {
      where: { id: string }
      include: { users: { select: { id: true } } }
    }) => Promise<{ users: { id: string }[] } | null>
  }
  user: {
    findMany: (args: {
      where: { organizationId: string }
      select: { id: true }
    }) => Promise<{ id: string }[]>
  }
}

/**
 * Resolve the set of user IDs an assignment should target.
 * - USER  → [targetId] (or [])
 * - GROUP → the group's member IDs (org membership of the group is enforced by callers)
 * - ALL   → every user in the org; logs the count, warns past the threshold
 * - other → []
 */
export async function resolveAssignmentUserIds(
  db: AssignmentTargetsDb,
  assignmentMode: string,
  targetId: string | null,
  organizationId: string,
): Promise<string[]> {
  if (assignmentMode === ASSIGNMENT_MODES.USER) {
    return targetId ? [targetId] : []
  }
  if (assignmentMode === ASSIGNMENT_MODES.GROUP) {
    if (!targetId) return []
    const group = await db.userGroup.findUnique({
      where: { id: targetId },
      include: { users: { select: { id: true } } },
    })
    return group ? group.users.map((u) => u.id) : []
  }
  if (assignmentMode === ASSIGNMENT_MODES.ALL) {
    const users = await db.user.findMany({
      where: { organizationId },
      select: { id: true },
    })
    const ids = users.map((u) => u.id)
    if (ids.length > LARGE_ASSIGNMENT_WARN_THRESHOLD) {
      console.warn(
        `[assignmentTargets] ALL assignment resolved ${ids.length} users in org ${organizationId} (over ${LARGE_ASSIGNMENT_WARN_THRESHOLD})`,
      )
    } else {
      console.info(`[assignmentTargets] ALL assignment resolved ${ids.length} users in org ${organizationId}`)
    }
    return ids
  }
  return []
}
```

### `app/actions/rules.ts`

- Delete the local `resolveAssignmentUserIds` (lines 17-41).
- Add imports: `import { resolveAssignmentUserIds, ASSIGNMENT_INSERT_CHUNK_SIZE } from '@/lib/assignmentTargets'` and `import { chunk } from '@/lib/chunk'`.
- Update both call sites to pass `prisma` first: `resolveAssignmentUserIds(prisma, assignmentMode, targetId, organizationId)` (lines 222, 285).
- Replace the single `createMany` in `createRule` (lines 245-252) with a chunk loop:

```typescript
            if (userIds.length > 0) {
                for (const batch of chunk(userIds, ASSIGNMENT_INSERT_CHUNK_SIZE)) {
                    await tx.ruleAssignment.createMany({
                        data: batch.map((userId) => ({ ruleId: rule.id, userId })),

```

- Replace the single `createMany` in `updateRule` (lines 311-318) with a chunk loop over `toCreate`:

                if (toCreate.length > 0) {

                            data: batch.map((userId) => ({ ruleId, userId })),

- Replace the single `createMany` in `createTask` (lines 84-91) and `updateTask` (the `taskAssignment.createMany` block after line 165) with chunk loops, mirroring the rules.ts pattern but with `taskId`.
- Chunk the push lookup in `createTask` (lines 97-104) so the `IN (...)` clause is also statement-safe:

```typescript
                const sessions: { deviceToken: string | null }[] = []
                for (const batch of chunk(userIds, ASSIGNMENT_INSERT_CHUNK_SIZE)) {
                    const rows = await prisma.deviceSession.findMany({
                        where: { userId: { in: batch }, deviceToken: { not: null }, revokedAt: null },
                        select: { deviceToken: true },
                    })
                    sessions.push(...rows)
                }
```

(The rest of the push block — token mapping, `sendPushNotification` — is unchanged.)

## Error handling

Unchanged. Each action keeps its existing `try/catch` returning `{ error }`. A failing chunked insert inside the `$transaction` rolls the whole transaction back exactly as a single `createMany` failure would today. The push block stays fire-and-forget (`.then(...)`); chunking only makes its lookup robust on large orgs.

## Testing

New `tests/lib/assignmentTargets.test.ts` (Vitest), pure unit tests against a hand-rolled mock `AssignmentTargetsDb`:

1. **USER mode** → returns `[targetId]`; `[]` when `targetId` is null.
2. **GROUP mode** → returns the mocked group's member IDs; `[]` when group not found or `targetId` null.
3. **ALL mode** → returns all mocked org user IDs.
4. **ALL mode logs the count** → spy `console.info`, assert called with the count when at/under threshold.
5. **ALL mode warns over threshold** → mock `> 1000` users, spy `console.warn`, assert it fired and `console.info` did not.
6. **Unknown mode** → returns `[]`.

`chunk()` behavior is already covered by `tests/lib/chunk.test.ts`. The chunk-loop integration in the actions is verified by `npm run build` + the full suite; the action functions use the global Prisma singleton and are not unit-tested directly (consistent with the rest of `app/actions/*`).
